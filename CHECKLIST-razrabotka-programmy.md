# Чек-лист разработки полноценной программы

Практический план для создания корпоративного ПО уровня TransTrade: от идеи до эксплуатации и поддержки.

**Как пользоваться:** проходите этапы по порядку. Отмечайте пункты `[x]` по мере выполнения. Не переходите к следующему этапу, пока не закрыты критичные пункты текущего.

---

## Этап 0. Инициация и границы проекта

- [ ] Сформулировать проблему, которую решает программа (1–2 предложения)
- [ ] Определить целевую аудиторию (роли пользователей: логист, диспетчер, бухгалтер, водитель, администратор)
- [ ] Зафиксировать, что **входит** в первую версию (MVP), а что — во вторую и далее
- [ ] Оценить конкурентов и аналоги (TransTrade, 1С:Управление транспортом, облачные TMS и т.д.)
- [ ] Выбрать модель монетизации (разовая лицензия, подписка, модули, freemium)
- [ ] Определить платформы: Windows / Web / мобильные / все сразу
- [ ] Назначить ответственных: продукт, разработка, дизайн, тестирование, поддержка
- [ ] Согласовать сроки и бюджет первой версии

**Результат этапа:** документ «Концепция продукта» (2–5 страниц).

---

## Этап 1. Сбор и анализ требований

### 1.1 Бизнес-требования

- [ ] Описать основной бизнес-процесс «от заказа до оплаты» (as-is и to-be)
- [ ] Составить список сущностей: заказ, клиент, перевозчик, ТС, водитель, документ, платёж
- [ ] Определить статусы заказа и правила переходов между ними
- [ ] Описать типы документов (заявка, договор, счёт, акт, ЭТрН и т.д.)
- [ ] Зафиксировать отчёты, которые нужны руководству (рентабельность, задолженность, загрузка парка)
- [ ] Собрать требования по интеграциям (1С, АТИ, ЭДО, банк, SMS, карты)

### 1.2 Функциональные требования

- [ ] Разбить функции на **базовые** и **модульные** (как у TransTrade)
- [ ] Для каждой функции указать: кто использует, входные данные, результат, приоритет (Must / Should / Could)
- [ ] Описать сценарии использования (User Stories или Use Cases)
- [ ] Определить ограничения демо-версии (если планируется trial)
- [ ] Зафиксировать требования к многопользовательской работе и правам доступа

### 1.3 Нефункциональные требования

- [ ] Производительность (время отклика, число одновременных пользователей)
- [ ] Надёжность (резервное копирование, восстановление после сбоя)
- [ ] Безопасность (аутентификация, шифрование, аудит действий)
- [ ] Масштабируемость (локальная сеть → облако)
- [ ] Совместимость (ОС, версии .NET / браузеров, разрешение экрана)
- [ ] Локализация (русский язык, форматы дат, валют, НДС)
- [ ] Соответствие законодательству (152-ФЗ, ЭПД, реестр отечественного ПО)

**Результат этапа:** ТЗ / Product Requirements Document (PRD) с трассировкой требований.

## Этап 2. Проектирование архитектуры

- [ ] Выбрать тип приложения: desktop (WPF/WinForms/Electron), web (SPA + API), гибрид
- [ ] Выбрать архитектурный стиль: монолит / модульный монолит / микросервисы
- [ ] Спроектировать слои: UI → бизнес-логика → доступ к данным → интеграции
- [ ] Выбрать СУБД (PostgreSQL, MS SQL, SQLite для локальной версии)
- [ ] Определить схему хранения: одна БД на офис / облачная мультитенантность
- [ ] Спроектировать API (REST или gRPC) для web/mobile/интеграций
- [ ] Определить стратегию синхронизации офлайн ↔ онлайн (если нужен «Оффлайн Офис»)
- [ ] Спроектировать систему модулей и лицензирования
- [ ] Выбрать очереди/фоновые задачи (отчёты, рассылки, импорт)
- [ ] Спланировать логирование, мониторинг и обновления
- [ ] Нарисовать диаграммы: контекст, компоненты, ER-модель данных, ключевые sequence-диаграммы

**Результат этапа:** Architecture Decision Records (ADR) + схема БД + диаграммы.

## Этап 3. UX/UI и прототипирование

- [ ] Провести интервью с 3–5 потенциальными пользователями
- [ ] Составить карту экранов (sitemap / screen map)
- [ ] Описать пользовательские сценарии для каждой роли
- [ ] Создать wireframes ключевых экранов: список заказов, карточка заказа, справочники, отчёты
- [ ] Разработать UI-kit: цвета, шрифты, таблицы, формы, кнопки, статусы
- [ ] Сделать интерактивный прототип (Figma / Axure)
- [ ] Провести usability-тест прототипа и зафиксировать правки
- [ ] Определить принцип «минимум кликов» для частых операций (создание заказа, печать заявки)
- [ ] Спроектировать мобильный интерфейс (если в scope)

**Результат этапа:** утверждённые макеты + UI-kit + список экранов MVP.

## Этап 4. Подготовка инфраструктуры разработки

- [ ] Создать репозиторий и структуру проекта
- [ ] Настроить ветвление (Git Flow / trunk-based)
- [ ] Настроить CI/CD (сборка, тесты, артефакты)
- [ ] Настроить линтеры, форматирование, pre-commit hooks

- [ ] Настроить систему задач (Jira, GitHub Issues, YouTrack)
- [ ] Определить Definition of Done для задачи и для релиза
- [ ] Подготовить шаблоны: bug report, feature request, pull request

**Результат этапа:** команда может собирать и деплоить код одной командой.

## Этап 5. Разработка ядра (MVP)

### 5.1 База данных и доменная модель

- [ ] Реализовать миграции БД
- [ ] Создать сущности: контрагенты, заказы, транспорт, пользователи
- [ ] Реализовать CRUD для справочников
- [ ] Реализовать жизненный цикл заказа (статусы, история изменений)
- [ ] Добавить soft delete / архивацию записей
- [ ] Реализовать полнотекстовый или фильтрованный поиск

### 5.2 Бизнес-логика

- [ ] Подбор транспорта по параметрам (грузоподъёмность, маршрут, занятость)
- [ ] Расчёт стоимости (фикс, км, часы, тонны, доп. услуги)
- [ ] Контроль задолженности и частичных оплат
- [ ] Генерация номеров документов
- [ ] Валидация данных на уровне домена
- [ ] Аудит-лог действий пользователей

### 5.3 Пользовательский интерфейс (MVP-экраны)

- [ ] Авторизация и управление сессией
- [ ] Главная / дашборд
- [ ] Список и карточка заказа
- [ ] Справочник контрагентов
- [ ] Справочник транспорта и водителей
- [ ] Базовые фильтры, сортировка, пагинация
- [ ] Настройки пользователя и роли

### 5.4 Документы и печать

- [ ] Шаблонизатор документов (Word/PDF/HTML)
- [ ] Печатная форма заявки
- [ ] Счёт и акт (базовые)
- [ ] Экспорт в Excel/PDF
- [ ] Конструктор пользовательских шаблонов (можно во 2-й версии)

**Результат этапа:** рабочий MVP — можно провести заказ от создания до печати документов.

## Этап 7. Интеграции

- [ ] **1С** — обмен контрагентами, счетами, актами, банковской выпиской
- [ ] **ЭДО** (СБИС, Диадок) — выгрузка первичных документов
- [ ] **АТИ** — размещение грузов, проверка контрагентов
- [ ] **Банк** — импорт выписок, платёжные поручения
- [ ] **Почта / курьеры** (Почта России, СДЭК) — трекинг отправлений
- [ ] **Телефония** (Манго, Мегафон) — звонки из карточки клиента
- [ ] **GPS/Wialon** — отслеживание транспорта
- [ ] Webhook/API для сторонних систем
- [ ] Документировать каждый интеграционный контракт (формат, ошибки, retry)

**Результат этапа:** минимум 1–2 интеграции работают в staging и покрыты тестами.

---

## Этап 8. Безопасность

- [ ] Хеширование паролей (bcrypt/Argon2)
- [ ] RBAC — роли и права на уровне модулей и операций
- [ ] Защита от SQL-инъекций, XSS, CSRF
- [ ] HTTPS everywhere
- [ ] Шифрование чувствительных данных at rest (по необходимости)
- [ ] Политика паролей и блокировка после N неудачных попыток
- [ ] Резервное копирование по расписанию + проверка восстановления
- [ ] Журнал безопасности (login, export, delete)
- [ ] Соответствие 152-ФЗ (политика ПДн, согласия, локализация серверов)

---

## Этап 9. Тестирование

### 9.1 Виды тестов

- [ ] Unit-тесты бизнес-логики (покрытие критичных модулей ≥ 70%)
- [ ] Integration-тесты API и БД
- [ ] UI/E2E-тесты ключевых сценариев (создание заказа, печать, оплата)
- [ ] Нагрузочное тестирование (число пользователей, объём заказов)
- [ ] Регрессионное тестирование перед каждым релизом
- [ ] Тестирование миграций БД на копии реальных данных
- [ ] UAT — приёмочное тестирование с реальными пользователями

### 9.2 Тестовые сценарии MVP (минимум)

- [ ] Создать заказ → назначить перевозчика → сменить статус → распечатать заявку
- [ ] Добавить клиента → выставить счёт → зафиксировать оплату
- [ ] Два пользователя одновременно редактируют разные заказы
- [ ] Восстановление после падения сервера / потери связи
- [ ] Импорт 100+ контрагентов из Excel

**Результат этапа:** test report без блокирующих дефектов.

## Этап 13. Эксплуатация и развитие

- [ ] SLA поддержки (время ответа, severity levels)
- [ ] Процесс обработки багов и hotfix-релизов

- [ ] Анализ метрик: retention, churn, NPS, частота использования модулей

- [ ] Техдолг: выделять 15–20% спринта на рефакторинг

## Контрольные вехи (milestones)

| # | Веха | Критерий готовности |
|---|------|---------------------|
| M0 | Концепция | PRD утверждён, MVP scope зафиксирован |
| M1 | Прототип | Кликабельные макеты, 3+ интервью с пользователями |
| M2 | MVP Alpha | Заказ создаётся, печатается, хранится в БД |
| M3 | MVP Beta | 5+ пользователей тестируют 2 недели без блокеров |
| M4 | Release 1.0 | Документация, инсталлятор, лицензия, поддержка |
| M5 | Release 2.0 | Модули, интеграции, мобильное/облако |

## Риски — проверить заранее

- [ ] Недооценка сложности интеграций (1С, ЭДО) — заложить отдельный спринт на каждую
- [ ] «Вечный MVP» — жёстко ограничить scope первой версии
- [ ] Игнорирование UX — логисты работают 8+ часов в программе, UI критичен
- [ ] Отсутствие миграций данных — клиенты не перейдут без импорта из Excel/1С
- [ ] Без тестов на реальных объёмах — падение на 10 000+ заказах
- [ ] Юридические требования к ЭПД/ЭТрН — уточнить актуальные форматы и операторов

## Минимальная команда для полноценного продукта

| Роль | Задачи |
|------|--------|
| Product Owner | требования, приоритеты, приёмка |
| Backend-разработчик | API, БД, интеграции, лицензии |
| Frontend / Desktop | UI, отчёты, печатные формы |
| QA | тест-план, автотесты, регресс |
| DevOps | CI/CD, сервер, backup, мониторинг |
| UX/UI дизайнер | макеты, usability |
| Technical writer | документация (можно part-time) |
| Support | 1-я линия после запуска |

*Для учебного/стартап MVP можно совмещать роли, но чек-лист лучше проходить полностью — так меньше «дыр» в продукте.*

## Быстрый старт (если времени мало)

Если нужна **учебная или demo-версия**, сфокусируйтесь только на этом подмножестве:

1. Этап 0 — концепция (1 день)
2. Этап 1 — 10 ключевых user stories (2–3 дня)
3. Этап 2 — простая архитектура: Web + PostgreSQL (1 день)
4. Этап 5 — MVP: заказы + контрагенты + печать заявки (2–4 недели)
5. Этап 9 — ручное тестирование 5 сценариев (2–3 дня)
6. Этап 11 — краткая инструкция пользователя (1 день)

Остальные этапы добавляйте итеративно после первого рабочего прототипа.
